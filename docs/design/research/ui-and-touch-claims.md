## Synthesis caveats

Coverage is uneven. Of the eight research questions, verified claims cover mainly accessibility, safe area and resizing, pixel-art scaling, telegraphing and noise visualisation, and touch confirm flows. Several areas have no verified, sourced claim behind them: gesture conflict resolution (pan vs drag path vs pinch), minimum touch target sizes, haptics, loupe aiming, long-press conventions, overlay budgets and layering of competing previews, timeline, threat-ledger and recap-card layout, pixel fonts and 9-slice panels, juice and playback speed, and planning-screen conventions (Payday 2, Door Kickers, FTL, Invisible Inc.). Recommendations for those areas are design judgement.

Source strength: the accessibility and platform claims come from primary, current sources (Apple HIG, XAG, MDN, AbleGamers). The game-design precedents are secondary: 2012-2013 interviews and reviews, a 2018 preview, and one fan wiki. Those quote the designers or describe shipped games, but they record particular versions. XCOM iOS controls may have changed in later updates.

Split votes: the claim that integer scaling based on device pixels is needed passed 2-1 and is partly an inference beyond MDN. The Into the Breach 'no hidden information or randomness' claim passed 2-1 because of Grid Defense and random spawns.

Four claims were refuted and excluded:
- XCOM iOS uses a drag path (0-3).
- XCOM felt cramped even on iPad (0-3).
- XCOM 2's phone touch targets need getting used to (1-2).
- AbleGamers' remedy is recolouring rather than fixing one presentation (1-2).

Implementation caveats: WebKit reports landscape safe-area insets that differ between Safari and standalone PWA mode, so test both. True integer scaling under Phaser's EXPAND mode may need a variable internal width or letterboxing. The colour-plus-pattern mapping for the safe-floor tiles is our application of the guidelines; the sources do not prescribe it.


## Open questions the run could not answer

- How should BankHeist resolve the gesture conflict between one-finger pan, drag-to-path, pinch zoom and long-press on a 16px-tile map? This research verified nothing about it. Options include a drag that starts on the selected crew member drawing a path while any other drag pans, or an explicit path mode.
- What overlay budget keeps the path, noise ring, shot cone, Watch wedges and safe-floor tiles readable at once on a phone screen roughly 320x180 logical pixels? Options include showing only the overlay for the active action at full strength and dimming the rest, or a per-layer toggle.
- What minimum on-screen size should tap targets and pixel-font text have on phones once the art is scaled? The Apple HIG 44pt and Material 48dp figures were not verified in this run. A 16px tile at a typical phone scale may fall below them, which would make the loupe or auto-zoom 'Act' camera necessary rather than optional.
- What do the proven mobile planning, timeline and recap layouts look like (Door Kickers planning, Invisible Inc. map, Into the Breach island map, a resume recap card)? None of these survived verification, so the planning screen and the schedule strip still lack sourced precedents.

**[Good Neighbors pixel font (CC0): designed to stay legible under nearest-neighbour and fractional scaling](https://opengameart.org/node/48712)**

**[MDN: Crisp pixel art look with image-rendering](https://developer.mozilla.org/en-US/docs/Games/Techniques/Crisp_pixel_art_look)**

- Default browser image scaling smooths pixel art by averaging neighbouring pixel colours, so pixel-art canvases need image-rendering: pixelated (crisp-edges and -webkit-optimize-contrast work only in some browsers). (supporting). Quote: "uses a smoothing algorithm that averages the colors of pixels to create a smooth transition between them"
- image-rendering: pixelated keeps edges crisp at arbitrary non-integer scale factors (e.g. 5.7x), but drawing into a canvas at non-integer ratios blurs the art. For example, a 128x128 image drawn into 100x100 maps each image pixel to 0.78x0.78 canvas pixels; the destination size must be an integer multiple of the source size divided by the scale. (supporting). Quote: "each image pixel will be drawn as 0.78x0.78 canvas pixels"
- Screen readers cannot read canvas content, so the canvas needs an aria-label or fallback content. This supports putting UI text in an HTML overlay rather than on the canvas. (supporting). Quote: "Canvas content is not accessible to screen readers. Include descriptive text as the value of the aria-label attribute directly on the canvas element itself or include fallback content placed within the opening and closing canvas tag."

**[Responsive Game UI: designing HUDs across screen sizes and orientations](https://www.abratabia.com/game-ui-design/responsive-game-ui.php)**

- Touch targets in game UI should be at least 44x44 CSS px (Apple) or 48x48dp (Google). The source suggests 48-56px as more comfortable for games, with at least an 8px gap between targets and 16-24px for critical actions. (central). Quote: "A finger on a touchscreen needs at least 44x44 CSS pixels (Apple's guideline) or 48x48dp (Google's guideline). ... 48 to 56px is more comfortable for game UI. ... A minimum gap of 8px between targets"
- A small visual icon (e.g. 24px) can get a 48px touch area through invisible padding, as long as that area does not overlap other targets. (supporting). Quote: "A 24px icon can have a 48px touch area through padding, as long as that area does not overlap other targets (paraphrased by fetch summary)"
- HUD offsets should include the CSS env(safe-area-inset-*) values so notches and other hardware features do not hide UI. (central). Quote: "env(safe-area-inset-*) variables report these intrusions"
- Anchor HUD elements to screen edges or corners and scale them with the viewport, not with fixed reference dimensions. A fixed 1920x1080 reference can make elements very small on small screens. (supporting). Quote: "The anchor-based layout pattern positions each UI element relative to a screen edge or corner"
- Many web games lock gameplay to landscape and allow portrait only for menus. Landscape keeps the left-right viewport arrangement but leaves less vertical room for the HUD. When touch is detected, targets should grow and tap should replace hover. (supporting). Quote: "Many web games lock to landscape orientation for gameplay and allow portrait for menus."
